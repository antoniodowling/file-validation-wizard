# Coverage and report interpretation

The BAI2 candidate now uses [bai2-candidate-1.1.0.json](bai2-candidate-1.1.0.json), schema-3 exports, and the [source scope](../BAI2_SOURCE_SCOPE.md). The [1.0.0 snapshot](bai2-candidate-1.0.0.json) and [original fixture manifest](../../demo-files/bai2/manifest.json) remain historical evidence. Revision 1.1.0 applies class-aware signs from base BAI Version 2 while retaining candidate code placement and limits. Unqualified funds/currency/code/transport scenarios receive no validity verdict; malformed numeric/layout prerequisites suppress dependent control checks.

For BAI2 monetary checks and controls, a skipped required occurrence makes the aggregate check `not-evaluated` even when another occurrence passed. Any actual failed occurrence still makes the aggregate `failed`. Successfully evaluated occurrences remain in the report. This uses the existing check states and schemas; it is bounded BAI2 prerequisite tracking, not completion of #51's cross-parser evidence work.

`ruleset-2.0.0.json` preserves the historical coverage of all nine DEMO profile versions. Current EDI coverage is separately frozen in [edi-ruleset-2.1.0.json](edi-ruleset-2.1.0.json); ISO remains at 2.0.0 in this change. `npm run export:coverage` now emits only the current EDI revision. Never regenerate a historical snapshot to describe changed behavior. The same coverage is embedded in every run and export, so a moved URL does not erase the meaning of a historical report.

PASS means the matching profile's promised checks completed with no errors or warnings. PASS WITH WARNINGS means those checks completed with advisory warnings. FAIL is a completed assessment with a failed prerequisite or rule; dependent checks are explicitly not evaluated. Unsupported XML versions/encodings or multiple complete EDI interchanges receive no validity verdict. Read, decode, engine, resource and timeout failures are incomplete, with no completed assessment or result export. The UI keeps previous-run results and source out of incomplete runs.

Check evaluations are distinct from occurrence results: one EDI control/version rule can evaluate many envelopes. UI error/warning counts count finding occurrences; check counts and skipped states are in the coverage details/JSON. `ordinal` identifies an occurrence only inside its run. Rule IDs retain their subject; ruleset 2 changes semantics and must not be compared to ruleset 1 without its snapshot. Existing legacy location mapping is isolated to reports without schema 2; it cannot establish new validity.

CSV export schema 2 retains the original first ten columns and adds repeated provenance columns plus row kinds. `evaluation-occurrence` rows contain performed checks, including passes; `check-state` rows record suppressed evaluations. The first data row carries the complete coverage/exclusions/check snapshot; later rows reference its coverage revision. JSON schema 2 retains nested coverage, checks, occurrence locations and provenance. NACHA retains and rejects a UTF-8 BOM; XML/EDI coordinates use their decoded source after BOM removal. Coordinates are half-open zero-based UTF-16 offsets into the original decoded source, never byte offsets. Lines/columns are one-based. Context, exact, parser-position, file-wide and unavailable are explicit. A parser stop may follow the cause. XML namespace mismatch uses root context, not a falsely exact namespace highlight.

## Version-specific usage

Select the exact profile/version listed in the snapshot before loading a file. XML requires that exact namespace, one Document, one matching message container, one group header, scalar MsgId/NbOfTxs and payment information. These are a **DEMO structural subset**, not XSD validation. EDI retains the existing 004010/005010 DEMO pairs, validates envelope ownership/counts/controls, and excludes ST03 implementation-guide requirements. The 008030 profile has no qualified ISA12 mapping and yields unsupported/no verdict after structural checks; malformed envelopes still fail. Single-character CR/LF terminators are supported for standalone 005010. See [EDI source decisions](../EDI_SOURCE_SCOPE.md) for qualification and transport boundaries.

EDI remains export schema 2 and BAI2 remains schema 3. JSON preserves the specific unsupported `executionReason`; the existing CSV schemas omit that field. Issue #51 owns that shared export defect and schema migration. This delivery does not claim the CSV-reason acceptance item is complete, and does not rewrite historical schema meaning.

The sample helpers used by tests and the manually uploaded demo files are synthetic wiring examples for each selected version; there are no built-in sample-loading buttons. They are not complete payment instructions or independent conformance fixtures. Every selected profile links to its Huntington format-family guide. Profile coverage and exclusions define the assessed scope; the navigation link does not grant release approval. The catalog contains three ISO/X12 families with executable DEMO profiles and the ACH, BAI2 and CSV Wire candidate families. Each discloses support before version selection.

No report proves bank acceptance, funds availability, authorization, fraud approval, execution, or historical duplicate detection. Production activation requires revision-bound specification/ruleset/fixture/acceptance evidence plus every existing approval gate.

## ACH completion candidate coverage and schema 3

[ach-candidates-1.0.0.json](ach-candidates-1.0.0.json) freezes the four new profile revisions separately from every historical snapshot. Schema 3 preserves the first 22 CSV columns and appends Reported File Disposition, Reported File Qualifier, and Reported Batch Dispositions. These columns are blank for non-ACK and malformed/unsupported ACK runs. JSON adds optional `reportedDisposition` with file status/qualifier and batch status/reference pairs only after ACK syntax succeeds. These four ACH profile runs, including unsupported runs, identify schema 3; their predecessors and the ISO/X12 profiles retain schema 2 and its exact columns. BAI2 and CSV Wire also use schema 3 with blank disposition columns.

Bank-reported RECEIVED, ACCEPTED or REJECTED is independent of the format verdict. A valid REJECTED ACK and VAL ERROR can produce format PASS. Counts/hashes in ACK CTL describe the original file, so differences are admitted and are never compared with ACK line counts. The UI displays disposition separately and clears it on replacement, failure, format changes or incomplete runs. Metadata uses bounded text summaries (eight batches and shortened long values), with full reported values retained in exports; CSV cells remain formula-neutralized. Schema-3 source spans retain decoded-source coordinates and the existing explorer bounds. All fixed/ACK candidate decoders retain a BOM for explicit candidate rejection.

Returns admit ordinary 99/COR 98 layouts; specialized variants and unqualified code/SEC contracts carry no verdict. The current CTX reply-count preservation conflict is explicitly excluded rather than mislabeled as verified. The control-total scenario is one printable-ASCII 58-column record; transport policy is disclosed. Origination r2 checks declared healthcare and standardized descriptions without inferring absent real purpose. See the profile documents and fixture manifest for exact source/assumption boundaries.

## CSV Wire candidate coverage

[csv-wire-candidate-1.0.0.json](csv-wire-candidate-1.0.0.json) freezes the separate USD CSV Wire candidate and schema-3 exports. See [source/scope](../CSV_WIRE_SOURCE_SCOPE.md) and [fixtures](../../demo-files/csv-wire/README.md). It parses selected CSV input locally; report-export CSV handling is a separate code path. Historical BAI2 and other coverage snapshots are unchanged.

Date occurrences retain the UTC reference day used for the 30-day USD bound. Quoting/layout errors suppress dependent row checks; optional checks on successful runs are not applicable when absent. Unsupported scenarios discard all occurrences and carry no verdict, with all checks not evaluated. Resource/UTF-8 failures use the existing incomplete worker path. Parser-owned locations point to original quoted fields or explicitly labeled row context; values are not echoed in finding messages.
