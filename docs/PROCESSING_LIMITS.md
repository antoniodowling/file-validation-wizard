# Processing safeguards and upload stress kit

The current demo still has nine executable profiles. These safeguards do not expand validation coverage or introduce a Cancel button.

## Run policy

- The file picker and worker independently enforce the inclusive 25,000,000-byte limit. The worker checks bytes before decoding or parsing.
- A provisional 10,000 ms deadline starts when Validate is pressed and includes file reading and worker startup. The main page terminates the worker on expiry, invalidates pending reads, clears the run, and enables retry.
- Ten seconds is a conservative starting point, not a measured service-level guarantee. Adjust `VALIDATION_DEADLINE_MS` after representative foreground-browser and ReadMe testing. Background-tab throttling can delay the timer; the deadline is not a memory cap.
- File replacement/removal, format/version changes, and unmount invalidate the entire run, including asynchronous reads. Only the captured file/profile can produce that run's result.
- There is no new user-facing cancellation control. Replacement/removal/navigation retain their existing cleanup behavior.

## Failure categories

A completed validation can produce PASS, PASS WITH WARNINGS, or FAIL. Malformed XML handled by the parser remains a completed FAIL. A file-read error, excessive size, unavailable profile, invalid UTF-8, worker startup/runtime failure, engine exception, or deadline expiry is an incomplete run; results and CSV export remain unavailable.

The worker returns typed failure codes. Unexpected engine exceptions do not forward raw exception text, which could contain source-file values. Syntax findings continue to use the existing safe text rendering.

## File explorer budgets

Explorer work is optional enrichment after validation completes. If it fails or exceeds its separate 10-second preparation window, completed results and CSV export remain available.

The current provisional limits are 5,000,000 decoded characters for a full viewer document and the companion location index, 250,000 characters for the longest line in full-view mode, 12,000 characters for an excerpt, 32 related targets per finding, and 10,000 literal source-search matches. Files outside the viewer or long-line budget use an explicitly scoped original-source excerpt. Findings outside the index budget use an explicit unavailable location instead of a guessed highlight. These values are implementation guards, not measured browser support claims; see [FILE_EXPLORER.md](FILE_EXPLORER.md).

## Generate the upload kit

A ready-to-use generated archive is committed at [`demo-files/hnb-validator-stress-files.zip`](../demo-files/hnb-validator-stress-files.zip). It includes all 14 upload files, instructions, expected outcomes, checksums, and the initial local measurements described below.

From an absolute repository/worktree path, run:

```sh
cd /absolute/path/to/HNB-File-Validation-Wizard
npm run generate:stress-files -- /private/tmp/hnb-validator-stress-files
```

Use a dedicated output directory: regeneration replaces the known generated files there. Large generated payloads stay outside Git; the committed generator and its tests reproduce all 14 cases. `README.md` and `manifest.json` in the output identify each file's format/version, purpose, expected behavior, exact bytes, and checksum.

The kit covers small XML/EDI baselines, empty XML, invalid UTF-8, prohibited declarations, late malformed XML, 24,999,999/25,000,000/25,000,001-byte boundaries, 50,000 XML payment blocks, 5,000 nested XML levels, 50,000 EDI transactions, a 5 MB EDI element, and 250,000 additional short EDI segments.

All data is synthetic. These are stress inputs for limited demo checks, not standards-conforming payment fixtures. Run standard cases first, then the deep/dense cases individually in a local preview or ReadMe draft. Browser memory exhaustion is still possible despite a time limit. No input is guaranteed to force a timeout on every machine; deterministic deadline tests use a silent worker instead.

## Test interpretation

`tests/worker-request.test.ts` checks the worker byte boundary, decoding failures, malformed XML, and engine exception handling. `tests/run-lifecycle.test.ts` tests deadline termination, retry, stale reads/messages, invalidation, and failure presentation with a simulated worker and fake clock. `npm run test:stress-files` verifies generated bytes, encoding, manifest hashes, and EDI header positions.

For each manual upload, record browser/version, local versus ReadMe environment, elapsed time, result or failure message, responsiveness, and successful recovery using the small baseline. Actual browser and ReadMe results are required before claiming a supported performance envelope. Node worker measurements can guide investigation but do not establish browser memory usage or hosted acceptance.

## Initial local measurements

Single-run diagnostic measurements on Node v26.5.0/macOS used the bundled worker in fresh Node worker threads, a 10-second parent watchdog, and a deliberately restricted 256 MB old-generation heap. Small baselines took 17–42 ms; 50,000 XML blocks took 175 ms, 50,000 EDI transactions 99 ms, a 5 MB EDI element 18 ms, and 250,000 extra EDI segments 92 ms. These are local observations including startup, not browser budgets.

The 24,999,999-byte and 25,000,000-byte XML text-node cases exhausted that artificial heap cap after approximately 1.2–1.4 seconds. The 5,000-level XML returned ENGINE_ERROR in 23 ms. The 25,000,001-byte input returned FILE_TOO_LARGE before parsing. Empty and malformed XML and prohibited declarations returned completed FAIL; invalid UTF-8 returned INVALID_ENCODING. No case reached the deadline. Retain the 25 MB limit provisionally; actual browser memory and responsiveness remain unverified.
